### Phase 7 — the INR bug that blocked billing from 15 Jun to 30 Aug

> **Dodo cannot take RECURRING payments in INR.** Every subscription attempt ever made on this merchant failed with `"Payment mode not enabled for this merchant."` (15 Jun ×2, 30 Aug ×1) while both _one-time_ INR payments (Ghost Text, Aug 2025) succeeded. Same card, same product, same code: **INR fails, USD succeeds** — India's e-mandate rules on recurring card charges. Dodo geolocates Indian visitors to INR by default, so **every Indian customer would have hit this**. It is not an account or KYC problem — verification is complete and live payments are active.

- [x] **Fix: pin the checkout to USD.** `createCheckoutSession` now sends `billing_currency: 'USD'` + `feature_flags.allow_currency_selection: false`. Prices and Dodo products are USD anyway; the selector could only ever lead to a declined subscription. Verified: the session renders in USD on an Indian IP with the currency toggle gone.
- [x] **Fix: duplicate credit grant on first purchase.** Dodo fires BOTH `subscription.renewed` and `subscription.active` for an initial purchase (~0.5s apart) with distinct `webhook-id`s, so the dedupe table can't collapse them — `apply_plan_grant` ran twice, writing two `reset`/`purchase` pairs for one payment. The balance stayed correct (the grant wipes and refills) but the **ledger double-counted every purchase**, corrupting any revenue/credits-granted reporting. `grantSubscription` now skips the grant when the same plan + same billing period is already recorded active; renewals (period advances) and plan changes (plan differs) still grant.
- [x] **Fix: scheduled cancellation was invisible.** The normal portal "cancel at period end" flow emits only `subscription.updated`, which the dispatcher ignored — the row stayed `active`, so `/app/billing` could never show that a plan was ending. Only _immediate_ cancellation emits `subscription.cancelled`. Now handled, gated on `cancel_at_next_billing_date` so the `updated` events that accompany activation don't trip it. Access is untouched until `expired`.

> **Why NOT Hetzner + Cloudflare R2:** that was the original plan and the code for it was written and merged (the S3-compatible `S3_ENDPOINT` layer). Owner declined on the grounds of not wanting to hand card details to two unfamiliar providers. Replacement topology uses **only accounts that already existed**: compute on **Railway** (which ran this exact stack in Phase 9), and finished-render storage on **Supabase Storage via its S3-compatible endpoint** — which the `S3_ENDPOINT` work made a pure config change, no code edits. The Hetzner/R2 deploy artifacts were removed; the endpoint abstraction they motivated is what made this pivot free.

**Topology:** Vercel (web) → Railway (`api` + `worker` + `Redis`) → Supabase (Postgres, Auth, `raw-uploads`, `backgrounds`, **and `outputs` via S3 protocol**).

- [x] **Storage → Supabase S3-compatible endpoint.** `S3_ENDPOINT=https://<ref>.storage.supabase.co/storage/v1/s3`, `AWS_REGION=ap-northeast-2` (project region), `S3_OUTPUT_BUCKET=outputs`, credentials = a Supabase **S3 access key** (Storage → S3). Zero code changes — the `{ endpoint, forcePathStyle }` client added for R2 works unmodified.
- [x] **`outputs` bucket made PRIVATE.** It was still `public=true` from the Phase 9 design, so anyone holding an object URL could fetch a customer video unsigned. Now private; every read is presigned. Verified: unsigned public GET returns **400**, presigned GET returns **200**, and range requests return **206** (so `<video>` seeking works).
- [x] **Security: do NOT use Supabase "session token" S3 auth.** Authenticating the S3 client with `sessionToken = service_role key` works, but `getSignedUrl` then embeds it as `X-Amz-Security-Token` **in the URL** — every video link handed to a browser would leak full service-role DB access. Confirmed empirically. Dedicated S3 access keys produce a clean SigV4 signature with no token param. Note Supabase S3 access keys are **all-buckets, RLS-bypassing** with no read-only scope (unlike the R2 plan's read-only token) — so the key on Vercel is more privileged than ideal. _Follow-up: consider having the web presign via the API, or via storage RLS + the user's own JWT, instead of holding an S3 key._
- [x] **Compute → Railway.** Project `powerful-art`: `Rotpitch` (api, public domain), `worker` (start command `pnpm --filter @rotpitch/api start:worker`), `Redis` (with a persistent volume). Both app services build from `/apps/api/Dockerfile` on `main`. **Gotcha:** Railway injects its own `PORT` (8080) while the generated domain targeted 4000 → 502s; pinned `PORT=4000` to match.
